# UnityFS 资产格式与混淆恢复

面向「拿到一个 Unity 游戏的 AssetBundle 目录，要判断是否加密、能否离线解析」的任务。

## 1. 标准 UnityFS 头

```
0x00  char     signature[8]        "UnityFS\0"
0x08  UInt32BE version             6 / 7 / 8
0x0C  char     minPlayerVersion[]  以 \0 结尾，如 "5.x.x"
0x12  char     engineVersion[]     以 \0 结尾，如 "2019.4.29f1"（11 字符）
       Int64BE  fileSize           ← 自校验锚点
       UInt32BE compressedBlocksInfoSize
       UInt32BE uncompressedBlocksInfoSize
       UInt32BE flags
```

实测落到具体偏移（engineVersion = `2019.4.29f1` 时）：

```
0..7    "UnityFS\0"
8..11   version
12..17  "5.x.x\0"
18..28  "2019.4.29f1"
29      \0
30..37  fileSize (Int64BE)
38..41  compressedBlocksInfoSize
42..45  uncompressedBlocksInfoSize
46..49  flags
```

## 2. 判断是否加密：魔数直方图

对目录内**所有** bundle 取前 8 字节做分布统计。要点：

- 明文会出现 `UnityFS.`
- **出现"少量但非平凡"的近似图案（如 `....yFS.` 反复数百次）** → 这不是巧合。
  随机数据里三字节精确匹配的概率约 1/16M，几百次命中必然是**被变换过的 UnityFS**。
- 全随机 → 整体加密，或根本不是 Unity bundle。

```python
sig = {}
for f in bundles:
    head = open(f,'rb').read(16)
    k = ''.join(chr(b) if 32<=b<127 else '.' for b in head)[:8]
    sig[k] = sig.get(k,0)+1
```

## 3. 已知明文攻击：用 fileSize 自校验

**核心方法论：任何解密假设都必须由一个独立的结构字段验证，不能靠"看起来对"。**

标准 UnityFS 头的 `fileSize` 字段是最佳锚点——它必须等于磁盘上该文件的实际字节数。流程：

1. 由确定的 ASCII 串（`"Unit"` / `"yFS\0"` / `"5.x."` / `"19.4"`）反推密钥字节。
2. 用候选密钥解出 `fileSize`，与实际文件大小比对。
3. 一致才算破解成功。

### 实例：每文件独立的 4 字节字级 XOR

```
观测: 84 67 D5 44 | 79 46 53 00 | D3 09 BC 37 | 35 2E 78 2E | A9 09 8E 00 | 31 39 2E 34 | FD 3B 85 56 | 31 00 00 00
密钥: D1 09 BC 30 | 00 00 00 00 | D3 09 BC 30 | 00 00 00 00
明文:  55 6E 69 74 | 79 46 53 00 | 00 00 00 07 | 35 2E 78 2E | 78 00 32 30 | 31 39 2E 34 | 2E 32 39 66 | 31 00 00 00
      "Unit"       "yFS\0"       version=7      "5.x."        "x\0""20"      "19.4"        ".29f"         "1\0\0\0"
```

解出的 `fileSize` = `0x268674` = 2,524,788，与该文件实际大小**完全一致** → 解码正确。
顺带得出 `engineVersion = "2019.4.29f1"`。

### 如何判断密钥周期

逐字节解出密钥后，看**同一字节位置在不同 4 字节字上的取值**：

- byte0 呈 `D1, D3, D1, D3`（周期 16）
- byte1-3 恒定（周期 4）
- ⇒ 整体周期 16

**注意陷阱**：若只用 `fileSize` 校验，周期 8 和 16 可能都通过（因为该校验位置的密钥字节相同）。
必须再用**第二个独立字段**（如 `version` 合法值、`engineVersion` 可打印 ASCII）交叉确认。
本例中周期 8 会把 version 解成 `0x02000007`（非法）、engineVersion 解出 `,29f`（含怪字符），故排除。

## 4. 实测遇到的多形态陷阱

同一目录可能混有多种头部变体，看似三种格式，实则同一格式：

| 观测 | 实为 |
|---|---|
| `...yFS.`（offset 4 起） | 奇数字节字密钥 = `0x00000000` |
| 全不可打印，但 offset 4 = `86 b9 ac ff` | **同上**，只是奇数字节字密钥 = `0xFFFFFFFF`（即取反） |

`86 b9 ac ff` = `~("yFS\0")`。若分类器只看可打印性，会把同一格式误判成两类。
**判据：把每个 4 字节字与"标准明文"逐字求 XOR，得到密钥字，再看密钥字的分布模式。**

实测统计（9,612 个 bundle）：
- `UnityFS_xor` 4819 个
- 被误判为 `opaque` 3752 个 + `other_alpha` 1040 个（实为同一格式）
- 真正的异类只有 1 个自定义 `GFF\0` 容器（占 0.4%）

## 5. 密钥派生：先测结构，再决定是否读代码

在投入反编译前，先做三组廉价统计（读每个文件前 64 字节即可，秒级）：

1. **`key[0..7] = head[0..7] XOR "UnityFS\0"` 的取值分布**
   - 若跨文件恒定 → 固定密钥，直接建表解密全部
   - 若每文件唯一 → per-file 密钥，继续
2. **密钥是否周期**：试验 4/8/12/16/20/24/32/40/48 各周期，要求已导出片段在周期下自洽
3. **密钥与文件名的相关性**：文件名常是 MD5（内容寻址命名），比对 `key` 与 `md5(filename)` 各片段

实测结果（GF2）：
```
key[0..3] = 每文件唯一（2000 文件 → 2000 个不同值）
key[4..7] = 恒为 00000000 或 FFFFFFFF
⇒ 非周期、非固定；是"4 字节唯一值 + 固定 0/FF 填充"
```

**结论模式**：若密钥每文件唯一且非周期，则派生逻辑在代码里，单纯从密文无法推出——
此时应优先考虑「运行时捕获明文」，而不是硬啃密码学。

## 6. 保留魔数的"体加密"

另一种手法：**前 4 字节魔数保持正确，其余全部加密**，骗过只检查魔数的工具。

实测（IL2CPP 元数据）：
```
AF 1B B1 FA  ← 0xFAB11BAF 正确魔数
E8 7C 11 01  ← version = 0x01117CE8，合法值应为 24
```

**判据：魔数对但紧随其后的结构字段是垃圾值 → 体被加密。**
此时 Il2CppDumper 等静态解析器必然失败。

### 进一步的实测结论：可能是"按需解密"，没有可 dump 的完整明文

在运行时内存里扫描该魔数，命中处的 `version` 字段**仍是垃圾值**，
且所在区间大小恰好等于磁盘文件大小（17,924,096 字节，一份 `r--`、一份 `rw-`）。

⇒ **游戏把加密文件 mmap 进内存，按需解密单个元数据结构**，不存在一份解密后的完整 blob。
这类实现下，"dump 解密元数据再离线解析"这条路是断的。

**替代方案**（按代价排序）：
1. 用同版本发行的**托管程序集**提供类型/方法/字段名（IL2CPP 与托管元数据信息等价），
   再从 `GameAssembly.dll` 解析 `Il2CppCodeRegistration` 的 methodPointers 表补上地址。
2. Hook 元数据访问函数，逐结构捕获解密结果。
3. 放弃名称，直接对原生代码做 Ghidra 分析（用字符串 xref 定位关键函数）。

## 7. 检查清单

- [ ] 魔数直方图：几类格式？是否只是同一格式的密钥变体？
- [ ] 用 `fileSize` 自校验解密假设
- [ ] 用第二个独立字段（version / engineVersion）交叉确认密钥周期
- [ ] `key[0..7]` 跨文件分布：固定 / 周期 / 每文件唯一
- [ ] 密钥与文件名、文件大小的相关性
- [ ] 若密钥每文件唯一 → 优先考虑运行时捕获，而非离线破解
- [ ] 区分「文件头加密」与「整体加密」：正文熵无法区分（压缩数据本身高熵），
      要看能否解析出 block info 并解压

## 8. 不要假设引擎版本串：从最前 4 字节直接反推密钥

**这是一个让方案从"卡死"变成"通"的关键简化。**

早前做法：假设 `engineVersion` 是某个已知串（如 `2019.4.29f1`），构造候选明文头，
再按偏移解 `fileSize`。**该做法很脆**：引擎串长度可变（实测有 `"0.0.0"` 这种非标准值），
偏移一错全盘失败。

**正确做法**：只依赖最前 8 字节这个恒定已知明文。

```python
K   = head[0:4] XOR b"Unit"          # 4 字节密钥，直接得出
w1  = head[4:8]
PAD = b"\x00\x00\x00\x00" if w1 == b"yFS\x00" \
      else b"\xff\xff\xff\xff" if w1 == ~b"yFS\x00" else None
key8 = K + PAD
```

之后用解出的 `fileSize` 与实际文件大小比对即可验证。
实测在 400 个样本上 **394 个通过（98.5%）**，无需知道引擎版本。

### 判据优先级
`fileSize` 是最强锚点（唯一、可精确比对）。`version` 和 `engineVersion`
是弱锚点——**当它们解出"看起来不对"的值时，先怀疑密钥细微偏差，而不是直接否定假设**：

实测解出 `version=0x02000007`、`engine="2019.4,29f1"`，两处都只在所属字第 0 字节偏 `0x02`
⇒ 真实密钥流是 16 字节周期 `[K][PAD][K^2][PAD]`，而不是 8 字节。
**这种"固定偏移的固定偏差"是周期判错的典型指纹。**

## 9. 正文加密判定：用成品解析器当判据，不要手写 LZ4

**教训：手写 LZ4 + blocksInfo 偏移逻辑极易出错，而且难自证。**
本项目手写解析器连**明文** bundle 都解不开（blocksInfo 偏移或 LZ4 解码有 bug），
一度差点把"我的 bug"误判成"正文加密"。

**正确做法：装成品解析器当判据。**

```powershell
pip install UnityPy
```

```python
import UnityPy
UnityPy.config.FALLBACK_UNITY_VERSION = "2019.4.29f1"   # 见下
env = UnityPy.load(path_or_bytes)
n = len(list(env.objects))     # n > 0 即解析成功
```

### 必设兜底版本
若 bundle 的 `engineVersion` 是 `"0.0.0"` 等非法串，UnityPy 会抛
`No valid Unity version found`。**必须显式设置**：

```python
UnityPy.config.FALLBACK_UNITY_VERSION = "2019.4.29f1"
```
（版本取同 LTS 线即可，用于选择序列化格式，不必与资产完全一致。）

### 判定流程
对同一密文构造多个变体，逐个喂给 UnityPy，看哪个 objects > 0：

| 变体 | 含义 | 成功则说明 |
|---|---|---|
| 解密前 64/256/512/… 字节，正文原样 | 只有头被加密 | **头加密，正文明文** |
| 用同一密钥流解密整个文件 | 全文同密钥 | 密钥流可外推 |
| 参数组合扫描（key8/key16 × 多个长度） | 覆盖周期不确定性 | 最佳方案 |

**全部失败 ⇒ 正文用未知方案另行加密**，头密钥流外推无效。
此时离线解密不可行，应转向「运行时捕获明文」。

实测结论：GF2 的 `LocalCache` bundle 正文确实另行加密（3 个样本 × 2 密钥假设 × 10 种长度，
全部 `LZ4BlockError`），而 `StreamingAssets/aa/` 下的 bundle 是明文、可直接解析。

## 10. 两个目录可能完全不同的保密级别

同一个游戏里，不同来源的资产目录保密级别常常不同，务必分别验证：

| 目录 | 常见保密级别 |
|---|---|
| `StreamingAssets/aa/<Platform>/*.bundle` | 通常**明文**（Addressables 本地引导包） |
| `LocalCache/.../AssetBundles_*/*.bundle` | 常**加密**（热更新下载内容） |
| `*_Data/*.assets`、`globalgamemanagers` | 可能**局部加密**（实测：前 0x35728 字节混淆，其后明文） |

「局部加密」的判据：在某偏移之前查不到任何已知可打印串，之后突然出现大量
（如 `"UnityEngine"` 首次出现在 0x35728）⇒ 前段混淆、后段明文。

## 11. 先查第三方框架，但**必须验证它是否真的实现了保护**

游戏常用现成框架（ADV/对话系统、资源系统、热更新框架）。**这些框架的源码常常公开，
是最快的突破口**——但有个陷阱：

> **很多框架明确不提供加密/保护，把这件事留给开发者自己实现。**

实例：Unity 的 ADV 框架 **Utage（宴）** 有 `Utage.Crypt`（含 `EncryptXor`/`DecryptXor`），
很容易让人以为它就是资产解密器。但其文档明确写着：
「暗号化はしてくれません」——**Utage 不对 AssetBundle 加密**，需开发者自行用
`CustomLoadManager` 实现。

⇒ 该项目的资产加密其实是**游戏自研**，`Utage.Crypt` 大概率用于存档或剧本文本。

**正确流程**：
1. 从字符串表认出框架名（类型名前缀、命名空间、`#US` 里的日志前缀）
2. 查其公开源码/文档，看它是否**真的**实现了目标保护
3. 只有确认后才把它的加密类当成分析目标

**反面教训**：先入为主认定框架的 `Crypt` 类就是资产解密器，
会浪费大量时间去反编译错误的目标。

## 12. 每文件密钥追查：把它当作假设检验题，逐条否定

当密钥每文件唯一时，按下列顺序做**廉价否证**（每个都是几秒到几分钟）：

| 假设 | 检验方式 |
|---|---|
| 固定密钥 | `K` 跨文件是否恒定 |
| 周期密钥 | 各周期下已导出片段是否自洽 |
| 由文件名派生 | `K` vs 文件名 hex 各 4 字节 / `md5(名字)` 各片段 |
| 由大小派生 | `K` vs `size` 的 LE/BE 4 字节 |
| 由内容哈希派生 | `K` vs `md5(前 N MB)` |
| 哈希 ⊕ 固定 salt | **统计 `K XOR 哈希片段` 的取值种类：=1 即破解** |
| 明文存于配置文件 | 用已知 `K` 在目录内做字节搜索 |

**全部否定本身也是有价值的结论**：它把问题锁定为"密钥来自外部元数据或未知变换"，
从而排除掉一整类廉价方案，避免反复尝试。

### 别忽略位分布
若出现**低位趋于零、按 2 的幂衰减**的分布（如 `head[0]` 76% 为偶数，
`&7` 计数 0→124、4→79、2→63、6→40 递减），则说明该字段含**算术结构**
（对齐值/长度/指针类整数），**不是纯密文或加密哈希**。
这是最重要的离线突破口线索，应优先追查而不是当作噪声。

## 13. ❗ 资产加密 ≠ 清单加密：先穷举"哪些元数据是明文的"

这是**在动手破加密之前必须做的一步**，往往能把工作量砍掉一半。

游戏厂商通常把**内容**加密，却**不方便加密清单**——因为运行时需要快速查表。
于是常常出现这种局面：

| 对象 | 是否加密 | 实测（GF2） |
|---|---|---|
| 资产正文（bundle 内部） | **加密** | 9,612 个 bundle 正文无法离线解 |
| Addressables 主清单 | **明文** | `catalog_main_28495.bin` 59 MB，含 68,723 个 bundle ID，覆盖磁盘 97.3% |
| 游戏数据表 | **明文** | 2,288 个 `.bytes` 明文 protobuf，含完整资产路径 |
| 资源地址名 | **明文** | `Assets/ArtsResource/.../*.prefab`、`Avatar_Head_*` |
| IL2CPP 元数据 | 加密（按需解密） | 魔数对但 version 为垃圾值 |
| 托管程序集方法体 | 剥离/填充 | `MoveNext` 为空、异类同乱码 |

### 能带来什么

明文清单通常足以完成**「定位目标」**这一半工作：

- 哪个 bundle 装了什么（清单里的 bundle ID + 依赖关系）
- 目标资产的**完整路径/名字**（数据表里的 `Assets/...` 字符串）
- 场景与 bundle 的对应关系（Addressables 地址表）

于是 **Mod 的定位环节完全不需要解密**，只剩「取内容 / 换内容」需要运行时方案。

### 必查清单（按优先级）

1. **Addressables 清单**
   - `StreamingAssets/aa/settings.json`（明文 JSON，写明 catalog 位置、版本、是否禁用更新）
   - `StreamingAssets/aa/catalog.bin`（小，本地内容）
   - **`LocalCache/**/catalog_*.bin`**（大，远程内容——本项目 59 MB，覆盖 97.3%）
   - 判据：含 Addressables catalog magic、大量 32 位 hex 串、provider 类名
2. **游戏数据表**：`**/Table/*.bytes`、`**/Config/*`
   - 判据：明文 protobuf / json，含 `Assets/...` 路径串
   - 关键词搜索：`Assets/`、`prefab`、`mesh`、`Avatar`、`Character`、`Model`
3. **各目录的 `settings.json` / `*.json`**
4. 只有以上都拿不到定位信息时，才去破内容加密

### 一个反直觉的细节

catalog 里的**资源地址数量可能远少于 bundle 数量**，而且可能**几乎全是场景**。
本项目 833 个地址中 786 个是 `Assets/ArtsResource/Scene`。

⇒ **角色/模型这类内容可能不走 Addressables 路径寻址**，而是由自研资源系统
按内部资产 ID 从 bundle 取。此时资产名要从**游戏数据表**里找，不要在 catalog 里死磕。

**判据**：若 catalog 的地址集合覆盖不到你要找的资产类别，
就去翻 `Table/*.bytes` 之类的业务数据表，那里的字符串往往是完整资产路径。

## 14. 用「前缀归类统计」从明文数据表反推资产命名规范

**这是 name-based hook 的前提**：想按名字拦截资产加载，先得知道名字长什么样。

### 手法

对全部明文数据表做一次全量字符串抽取，然后**按标识符的下划线分段聚合**，
统计每个前缀的出现次数，按次数排序。

### 判读规则（本项目实测）

```
Avatar_Head_*    10623   ← 次数最高，是 UI 图集（头像），不是模型
Avatar_Bust_*      272
Avatar_Whole_*     106   ← 次数少但语义明确 = 3D 模型本体
Avatar_Gacha_*      61   ← 同上
Avatar_Half_*       12
```

**关键判据**：
- **次数极高**（上万）⇒ 通常是 UI/图标类资源，量大、按角色×状态平铺
- **次数中等偏低 + 语义明确**（`Whole` / `Gacha` / `Bust` / `Bind` / `Rig`）⇒ **3D 模型本体**
- 直接看数量最多的一类会误判成"主角资源"，实际上那是 UI

### 命名模式的常见结构

Unity 手游的角色资产常按 `<名><稀有度><序号><变体>` 拼：

```
Avatar_Whole_UllridSSR        Avatar_Gacha_LittaraSR
Avatar_Bust_LoreleySSR01      Avatar_Bust_Player_Male03
Avatar_Asteria_1_01           Avatar_Agent_2_02
```

⇒ hook 时用**前缀匹配**（`StartsWith("Avatar_Whole_")`）比精确匹配更稳，
既能覆盖全部角色，又不会被序号/稀缺度变体漏掉。

### 顺带要确认的事：合并/烘焙类

如果字符串里出现 `*Merger*` / `*Combiner*` / `*Baker*` / `BakeMesh`
（本项目：`SkinnedMeshMerger`、`SkinnedMeshMergerLOD`、`SkinnedMeshNode`），

## 16. 判断「加密到底覆盖多少字节」——不要默认全文件

发行包常见做法：**只加密前 32KB（或某个对齐块），其余保持明文**，
目的是让加载器能读头、又能让大文件保持流式读取性能。
若按"全文件 XOR"处理，会得到"头部全对、数据全错"的假象。

### 症状（本项目实测）

- 头部字段（signature/version/`size` 自校验）全部正确
- 能解出 block0，但从第 2 个数据块开始 LZ4 全部失败
- 改包写回后 Unity 直接报 `Failed to load ... File may be corrupted`
  （因为写回时把本该是明文的区域又 XOR 了一遍）

### 判据与手法：拿"下游格式解码"当边界探针

把前缀长度 N 当参数扫描，目标函数 = **下游结构能否被完整消费**：

```
for N in (0x2000, 0x4000, 0x8000, 0x9000, 0x10000, ...):
    plain = cipher[:N] XOR ks + cipher[N:]      # 只解前 N 字节
    ok = 所有 LZ4 块都能解出且长度等于表里的 uncompressedSize
```

本项目结果：`N=0x8000` 时 39/39、222/222 块全部解出，`N=0x8010` 立刻退化为 38/39。

**为什么用"全部块都解出"而不是"第一块解出"**：
第一块往往落在加密前缀内，单独解出无法区分"全加密"和"只加密前缀"。

### 配套的写回规则

- 加密端同样**只处理前 N 字节**；N 之后原样写明文
- 密钥派生用的 4 字节必须取**原密文**的头 4 字节；
  若误用明文头 4 字节（`"Unit"`）会派生出 X=0 的错误密钥流
- 自检：`decrypt_prefix(write(plain)) == plain` 且
  `cipher[:4] == 原始文件[:4]`，再外加"所有块可解码"的独立判据

### 更一般的教训

**「往返自校验」无法发现边界/密钥流只对了一半。**
`decrypt(encrypt(x)) == x` 在错误密钥流下也恒成立。
必须引入**外部消费者**（压缩流解码器、长度字段、独立解析器）作为判据，
它们的**失败位置**就是"从第几个字节开始不对"的直接证据。
