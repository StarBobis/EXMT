## 23. 把「每网格一副残缺骨架」还原成完整骨架（Unity 2021- 实测，GF2 / Unity 2019.4）

**适用**：把游戏里的带蒙皮网格导到 DCC（Blender 等）时，骨骼只有一部分、或者干脆没绑上。

### 23.1 先认清 Unity 的存储方式

| 事实 | 判据 |
| --- | --- |
| `Mesh.m_BindPose` + `Mesh.m_BoneNameHashes` 是**每个网格各自一份**，通常只含该网格权重里用到的骨骼 | 统计同一 bundle 里所有网格：本例 12 个网格 3…70 根，**并集 226 根**；`max(权重索引) == len(表)-1` |
| 长度必须相等：`len(bindposes) == len(boneNameHashes) == SkinnedMeshRenderer.bones.Length` | 逐个网格断言；武器包 5 骨 vs SMR 5 骨 |
| 骨骼身份只有 **CRC32 哈希**，没有名字、没有父子关系（Mesh 里） | `m_RootBoneNameHash` 只是其中一根的哈希 |

**结论**：想给 DCC 一副完整骨架，必须**把同一角色所有网格的表按哈希求并集**；想给名字/层级，必须去别处找哈希的来源（§23.3）。

### 23.2 哈希函数：`crc32(完整 transform 路径)`

```python
import zlib
h = zlib.crc32("root/Root_M/Spine1_M/Spine2_M/Chest_M".encode()) & 0xFFFFFFFF
```

- 是**路径**不是叶子名：同一个 `Elbow_L` 挂在不同父链下哈希不同。
- 验证方法（**必做**）：拿带 `Avatar` 的资源，它的 `m_TOS` 就是 `[(hash, "父/子/孙"), …]`；
  逐条比 `crc32(path)`，本例 **30/30 全中**，而 `crc32(叶子名)` 只有 1/5 命中。
- 这条一旦验证通过，**哈希就等于路径**：拿到路径就能命名 + 建父链，反之亦然。

### 23.3 名字与层级从哪来（本地优先级）

| 来源 | 拿什么 | 成本 |
| --- | --- | --- |
| `Avatar`（`m_TOS`） | 权威：`(hash, 角色相对路径)`，直接给名字 + 父链 | 每包一次解压 |
| 角色/武器 prefab 的 `Transform` 树 | 同样的路径，但要**去掉 prefab 多加的祖先**（见下） | 每包一次解压 |
| 自己造词表反查 | 兜底，命中率低（命名约定因项目而异） | — |

prefab 里的路径是相对 prefab 根的（`PrefabRoot/Armature/Bip001/Spine`），而哈希是相对**角色根**的。
所以把每条路径的**所有后缀**都登记成候选（`PrefabRoot/...`、`Armature/...`、`Bip001/Spine`、`Spine`），
用的时候只查网格真正有的哈希——不匹配的后缀不会被用到；CRC32 撞车的概率约 `候选数 × 骨骼数 / 2^32`（本例 < 1e-3）。

**扫描要快就得只读元数据前缀**：

```python
# 1) 只读文件头 128 KiB，解密 + parse blocksInfo
# 2) 只解压覆盖 SF 元数据（type list + object table）的前若干块，本例 768 KiB 足够
# 3) UnityPy.load(截断后的 SF 字节)：对象表能读，个别对象数据读不到就跳过
```
9613 个 bundle 的**全量**类型扫描（14 进程）**14 s**，把 Avatar+prefab 的路径全抓下来 **13 s**、约 5 万条。

### 23.4 DCC 侧：一副骨架 + 同名顶点组

Blender 的 Armature 修改器**只认名字**：顶点组名必须和骨骼名逐字相同，否则 0 个顶点受驱动
（本项目老的 bug 就是骨骼 `b000`、顶点组 `b0`）。

```
骨架 = 并集（顺序稳定：按第一次出现的顺序；名字 = 真名，取不到时用 `bone_<8位哈希>`，必须去重且 ≤63 字节）
每个网格：local[i] -> 骨架索引[i]，顶点组名 = 骨架骨骼名
          建组要建**该网格自己那张表的全部骨骼**（游戏只允许它绑这些），不是只用到的
          父级 + Armature 修改器；bind 就是 rest（Blender 里 pose==rest 时不形变，天然无损）
```

导出方向：**名字 → 哈希 → 目标网格的骨骼索引**。索引不要跨文件传递（每个网格一套），
哈希才是稳定的；给外部物体（glTF 进来的）打包时，先问目标网格的表，再把组名还原成哈希。

### 23.5 两个会让「往返不逐位一致」的坑

| 坑 | 现象 | 修法 |
| --- | --- | --- |
| 并列权重排序 | 权重完全相同的影响槽被换了位置，`bones` 索引对不上 | 按 `(权重降序, **索引升序**)` 排（游戏数据就是这么排的） |
| 无谓归一化 | 权重和 ≈1 时再除以 total，差 1 ULP（1.2e-7） | `abs(total-1) < 1e-6` 时原样写回 |
| 通道维度 | 有些网格只声明 2 个影响槽（`BlendWeight.dimension == 2`），一律写 4 会让形状不一致 | 按 `m_Channels[12/13].dimension` 写 |

### 23.6 验收清单（缺一不可）

- [ ] 每个网格：`顶点组数 == 自己那张表的骨骼数`，且**每个组名都能在骨架里找到**
- [ ] `受驱动顶点数 == 顶点数`（不是"看起来对"）
- [ ] 转动一根主链骨骼，网格**真的动**（本例 Spine1_M 转 25° → 4618/4618 顶点位移）
- [ ] 不改动直接导出：`weights`/`bones` **逐位相等**（不是近似）
- [ ] 打包回 bundle 再解出来：顶点流 + typtree（`m_BindPose`、`m_BoneNameHashes`）**全等**
- [ ] 骨骼数 = 并集数，不是第一个网格的数

## 判据：权重到底有没有进导出的网格（2026-10-19）

外部模型（MMD/VRM/别的游戏）替换游戏网格时，"权重看起来对"和"权重真的写进文件了"是两件事。
只看 Blender 里的顶点组会被骗：**导出端要能把组名解析成目标骨骼表的槽位**，解析不到就静默丢。

解 `npz` / 顶点流后看四个数，任一为 0 就是废数据（游戏里表现为**模型完全不显示**，不是位置错）：

```
weights.sum(axis=1)  ->  全部 ≈ 1.0          # 行和
bones.max()          ->  < len(bone_hashes)  # 索引不越界
bone_hashes, bindpose->  非空                # 骨骼表与绑定姿势
len(set(bones[weights>0]))  ->  > 0          # 真正参与加权的骨槽数
```

根因模板：外部物体的骨骼表属性（本例 `exmt_bones`）不存在 → 目标表为空 → 名字解析全失败 →
每条影响被 `dropped += 1`。**修的时候顺手看那个 `dropped` 计数器**：它经常写在顶点循环内部，
每轮被重置，于是永远报 0，错误就彻底静默了。

## 判据：同名网格的跨包差异不止 UV/可读性，还有骨骼表（2026-10-19）

同一个网格名可能出现在多个 bundle，各副本**烘焙用的骨骼表可以不同**：

```
旧表: root/Root_M/Hip_M/Hip_R/HipPart1_R/...     # Hip_M 是 Hip_R/Hip_L 的父
新表: root/Root_M/Hip_R/HipPart1_R/...           # Hip_M 被删，层级重组 → 各段哈希全变
```

- 打包时按哈希重映射能救回**共有**的骨，缺的那几根的影响**直接丢**（实测丢 30% 权重、
  1954/12734 顶点全部影响丢失 → 塌到原点）。
- **不要用"短名/末段名"兜底**：实测 60.0% < 按哈希的 69.6%（大量骨名本身就是 `bone_<CRC32>`，
  根本没有可读短名）。要心里有数就**逐副本量**：`kept_weight` 和 `orphan_vertex_count`。
- 要全覆盖只能"按每个副本自己的表各导一份 patch"，不是靠匹配算法。

## 判据：外部模型的材质槽数必须 ≤ 目标网格的材质数（2026-10-19）

导出时"子网格编号 = 源模型的材质槽号"，而 Unity 的材质列表属于**被替换的那个网格**。
材质索引解析不到的子网格**直接不画**——Blender 里完全看不出来。

- 先量目标：`exmt_core matinfo <bundle> <mesh>` → `submeshes`（`c_VepleySSR01_slg_cloth_*` 是 4）
- 再量源：模型实际用到几个材质槽（MMD 常见 10~20）
- 实测代价：Sally 20 槽填进 4 槽的网格 → 丢 **6803 / 14568 面**，两条前臂和双手消失，
  而相邻槽位的配饰还在 → 画面表现为"手环浮在空中的断肢"
- 修法：按面数把源槽合并到目标槽数（一分为二没有损失），代价是部位会用错材质

## 判据：`m_DataSize` 是三个连续流，顶点步长要实测（2026-10-19）

```
s0  count x 40   position(12) + normal(12) + tangent(16)
s1  count x 20   colour(16) + uv0(4)
s2  count x 32   weights(16) + bones(16)
```

`len(m_DataSize) / vertex_count == 92` 是**三个流之和**，不是步长。
要拿真 stride：把**解码后的顶点位置**在 `raw` 里 `find()`，连续命中的偏移差值就是它（本例 40）。
只改 stream 0 就能"隐藏"网格（缩到原点），拓扑/权重/索引全不用动。

## 判据：同名网格的骨骼表可能差一个"代际"，按哈希 + 短名两级匹配（2026-10-19）

游戏更新常删掉一层中间骨（本例 `Hip_M`），于是它下面每条路径的 CRC32 全变，但**短名不变**：

- 先量：两份表的**短名集合**是否相同（本例 126 根里 123 根相同，12 个短名各两个哈希）
- 匹配顺序必须是 **① 哈希 → ② 短名末段**（“只用短名”会退化到 60.0%，低于纯哈希的 69.6%——哈希命中是精确的，短名只是兜底，顺序颠倒就变差），
  只按哈希会丢 1954/12734 个顶点的全部驱动；两级合起来 → **0 个无驱动顶点**
- 名字来源：`bonenames.json`（hash → 全路径），取 `rsplit("/", 1)[-1]`
